# FK Pickers on Generated Create/Edit Forms — Plan

**Pairs with:** `FK_PICKER_REQUIREMENTS.md` (v0.5)
**Version:** 0.5 (post-CRP R2 — mirrors REQ v0.5; R1 applied 12 suggestions, R2 applied 10, rejected 0)
**Date:** 2026-08-14
**Status:** authored, not implemented (no code written by this pass)
**Id convention:** FRs are `FR-1…FR-10` (det-req extraction); the `FR-FK-n` alias is for code comments
and cross-doc citation, matching `FORM_SUBMIT_BEHAVIOR`'s `FR-n` ↔ `FR-FS-n` in `htmx_generator.py`.

> **Shape of the work.** Not a widget change. One shared schema derivation (S1), one template
> rendering change (S3), one runtime helper threaded to **four** route call sites (S4), and two
> guards — existence validation and tenant scoping (S5/S6). Steps are ordered and acyclic: each
> depends only on earlier ones. S1 and S2 are strictly refactor-with-no-output-change, so they can
> land and be verified before any behavior moves.

## S1 — `fk_targets()` — the single FK-target resolver (FR-2)

| File | Change |
|------|--------|
| `src/startd8/languages/prisma_parser.py` | Add `fk_targets(schema, model_name) -> Dict[str, Tuple[str, str]]` mapping `fk_scalar → (target_model, ref_column)` by scanning each field's `@relation(fields:[…], references:[…])`. Move `_REL_FIELDS_RE` / `_REL_REFS_RE` here as the single home for the relation-attribute grammar. The resolver is **composite-complete**: it emits one entry per zipped `(field, reference)` pair, exactly as `_fk_map` does today (L164–170, documented at L150), and it excludes only list relations (which name no FK scalar). It does **not** carry the picker's composite exclusion. |

Chosen home rationale: this is pure schema derivation with no codegen concern, and both consumers
(`sqlmodel_renderer`, `htmx_generator`) already import from `prisma_parser` — so no new module and no
import cycle. Returns the **model** name (`f.type`), not the lowercased table name, because the
picker must query `select(Member)`; the table name is a rendering detail of one consumer.

**Resolver domain vs picker domain — corrected by CRP R2 (R2-S1).** An earlier version of this step
told the resolver to "skip composite FKs (len > 1)", which contradicted S2's promise to keep `_fk_map`'s
composite zip: a composite-skipping resolver hands S2 a strictly smaller map, and the re-expressed
`_fk_map` would emit **no `foreign_key=`** for any composite FK column — a dropped database constraint
shipped under a step whose whole premise is "no output change", and invisible to every original fixture
because all of them were single-column. The Non-goals exclude composites from the **widget**, not from
the **resolver**; that exclusion therefore lives in `is_fk_picker` (S3a), and the resolver's contract is
completeness. S0's composite fixture is what makes FR-2's byte-identity Verify able to fire at all.

**Verify:** unit — `fk_targets` on the relation fixture returns `{"assigneeId": ("Member","id"), …}`
and **omits** `DueInstance.sourceId`; on the composite fixture it returns one entry per zipped pair
(no columns dropped), and `is_fk_picker` is False for every one of those columns so the form falls back
to text inputs per Non-goals.

Note (e) is a real behavioral coupling planning surfaced: the existing hint exists *because* the
field was a text box. Leaving it would tell a user to paste an id into a dropdown. Two constraints
CRP R1 added and both are load-bearing: keying the change on L614's suffix predicate would also
silence the still-correct hint on `DueInstance.sourceId` (the exact suffix trigger FR-1 rejects), and
*deleting* rather than replacing the hint drops the control's `aria-describedby` — an FR-FH-11-visible
accessibility regression on precisely the fields this change touches. (e) now has an FR home in
**FR-1**, so it is verified rather than being untested plan-only work.

Labels are **not** resolved in the template — the route supplies `(value, label)` pairs (see S4), so
`form.html` gains no `display.yaml` dependency and its `htmx-form` dep-set is unchanged (FR-10).

**Verify:** unit on rendered template text — `assigneeId`/`memberId` are `<select>`;

## S4 — Options helper + all four route call sites (FR-3, 4)

| File | Change |
|------|--------|
| `src/startd8/backend_codegen/htmx_generator.py` | (a) Generate a per-entity `_options_<e>(session)` helper into `web.py` returning `{field: [(value, label), …]}` — one query per picker field: `select(Target)`, value = ref column, label = `_default_label_field(target)` value else the raw id (FR-4, reusing the existing `_LABEL_HEURISTIC`, L392–398). Ordering is **applied in Python over the fetched `(value, label)` pairs**, not as a SQL `ORDER BY`: "label-less rows last" is `NULLS LAST` semantics, and SQLite — the pilot's and the fixtures' engine — sorts `NULL` *first* on a plain `.asc()`, so a SQL-expressed order would make FR-4's ordering Verify pass or fail by backend (R2-S4). Sorting the pairs is free at the cardinalities (a′) permits, is dialect-independent by construction, and makes the `— unavailable —` placement of S3(f) trivially expressible. Two sub-cases, run separately: a target with **no label column at all** orders by the referenced column alone (already correct), while a target that **has** one with `NULL` in some rows is the `NULLS LAST` case. Without any ordering `select(Target)` returns engine/insert order, which makes FR-6's precedence and FR-3's / FR-9's assertions order-flaky and reorders the dropdown between environments (FR-4). The helper's field set is the same `is_fk_picker ∩ _writable_fields(…, human_only)` set S3(a) uses, so an owned FK column produces no key and no query. (a′) **Cardinality bound (FR-4):** the query is `limit N+1` against a single generated threshold constant — not a manifest key, not a flag; a target returning more than N rows supplies **no** options entry for that field, which routes it through S3(g)'s text-input fallback with its original hint. One constant, one degradation path, no new input. (b) Add `"options": _options_<e>(session)` to the context of **all four** `form.html` renders: `new_<e>` (L1129–1137), the `create_<e>` error re-render (L1157–1163), `edit_<e>` (L1189–1196), the `update_<e>` error re-render (L1205–1211). (c) `new_<e>` currently has **no session dependency** — add `session: Session = Depends(get_session)` to it, **iff that entity has ≥1 picker field**. The gate is per entity, following the `pdep` precedence three lines up (L1100, an empty string when `owner_field` is `None`), never per app. |

(c) is the one signature change planning found: three of the four sites already hold a session;
`new_<e>` does not, because until now the create form needed no data.

**Per-entity gating is the byte-identity gate — corrected by CRP R2 (R2-S2).** Read unconditionally,
(c) rewrites `def new_{e}(request: Request)` (L1130) for **every** entity — including the whole
**no-relation fixture**, which is the artifact S0 commits and S7 hash-compares, so S7's own FR-10
assertion would fail on its first run; and in a mixed schema it would hand a session to picker-free
entities. The correct construction already exists in the file at the site: `pdep` is per entity and
yields today's bytes when the condition is absent — the same presence-gating FR-10 and §0.2's Sotto
citation require. R1-S2 established *that* the auth posture changes and *where* it lands; this
establishes *which entities* it lands on, which is what makes or breaks byte-identity.

**Auth-posture change — stated, not implied (CRP R1).** The security-relevant half of (c) is not the
session but the `principal` that S6 adds alongside it. `GET /ui/<e>/new` is today the **only** form
route with no principal dependency even in a scoped app (`def new_{e}(request: Request)`, L1129–1137),
so in a scoped app it currently serves an anonymous 200. After S6 it does not — **for the entities that
acquire the dependency**, which per (c) and S6(c) are only those with a picker field and a scoped picker
target respectively. Anything relying on that
— a deployment with an anonymous create form, or any smoke script (including the pilot's curl block)
hitting `/ui/<e>/new` unauthenticated — breaks at **S6**, not at S4. This is an intentional behavior
change in generated *content* only; it changes no drift dep-set (asserted in S7), and naming it here
keeps FR-10's dep-set claim from being read as "no behavior change at all".

**Verify:** runtime (`tests/unit/backend_codegen/test_fk_picker_runtime.py`, following the
`test_*_runtime.py` convention) — a `TestClient` POST to `/ui/chore` that fails validation on
`anchorDate` returns a form whose `assigneeId` select still contains every Member option and
re-selects the submitted one. Assert on all four routes, not just `new`. Seed three Members out of
alphabetical order and assert the rendered `<option>` sequence is label-ascending with any label-less
row last **under SQLite** (the dialect the naive `.order_by` gets wrong); assert a Member named
`<script>alert(1)</script>` renders escaped; seed one row over the threshold and assert the field renders
a text input with its original hint instead of a select. The hand-enumerated four-route assertion is
backstopped structurally in S7 (count equality), not trusted on its own.

| File | Change |
|------|--------|

Its key set is the same `is_fk_picker ∩ _writable_fields(…, human_only)` set S3(a) / S4(a) use, so no owned column is existence-checked. (b) In both `create_<e>` and `update_<e>`, after `_form_errors` returns but **before the existing `if errors:` branch**, check each non-empty picker value against its target and **merge any miss into the same `errors` mapping** that branch already consumes — so the existing single re-render site handles it and the route count stays at four (FR-3). Placing the check outside `_form_errors` rather than inside it is deliberate: `_form_errors` is a pure
function over the form dict in every generated app, and giving it a session would change a shared
helper's signature for all of them.

**Position corrected by CRP R1 (R1-S3).** The earlier wording ("after `_form_errors` returns and
before `session.add` … the same path a `_form_errors` failure takes") named a position that is *past*
that path: the error re-render lives **inside** `if errors:` (L1158–1163, L1206–1211) and has already
returned by then, so checking afterward would force two additional `TemplateResponse` sites — taking
the count from four to six and handing the FR-3 defect (empty picker on the error re-render) two fresh
places to reappear. Merging into `errors` *before* the branch preserves the stated intent (a pure,
session-free shared helper) at zero cost and keeps exactly one re-render site per route.

**Verify:** runtime — `POST /ui/chore` with `assigneeId=not-a-real-id` returns **200** with a
field-level error on `assigneeId` and **no** row written (assert the table count is unchanged), not
the 500 an `IntegrityError` produces today; a valid id still returns 303 with the
`FORM_SUBMIT_BEHAVIOR` `Location`/`?created=` contract intact. Update path: `POST /ui/chore/<id>` with

## S6 — Tenant scoping of options and validation (FR-8)

| File | Change |
|------|--------|
| `src/startd8/backend_codegen/htmx_generator.py` | (a) Resolve the **target's** predicate independently of the owning entity's: `target_owner_field` is the tenant owner field when the *target* model is in `render_web`'s `scoped` set (L1322–1324), and `None` otherwise. Do **not** reuse the owning entity's `owner_field` (L1100) for the target — they are different values, and the owner's is `None` in exactly the dangerous cell. (b) When `target_owner_field` is set, add `.where(Target.<target_owner_field> == principal.id)` to `_options_<e>`'s query **and** to S5's existence check. (c) When **that entity** has ≥1 scoped picker target, add the `principal` dependency to every route that renders or accepts that picker — including `new_<e>`, which has none today. The gate is per entity, like S4(c) and like `pdep` (L1100): a picker-free or unscoped-target entity in the same schema keeps today's signature byte-for-byte (R2-S2). (d) **Mixed cell (unscoped owner × scoped target):** the owning routes resolve no principal today, so the step **adds one** — that is the normal, preferred outcome, and it must never emit a bare `select(<scoped target>)` or silently return empty options. The raise branch is the last resort, and if it is taken it must be a **named, typed generator error** that the drift layer converts into a status rather than propagating. A non-owned id reports the same "not a valid choice" field error as a nonexistent one (no existence disclosure), preserving the 404-not-403 posture. |

Scoping keys on whether the **target** entity is scoped, not the owning one — a scoped `Chore` may
point at an unscoped lookup table, and that must still populate. The converse cell is the dangerous
one and CRP R1 (R1-S5) made it explicit: "thread the existing `owner_field`" reads as if one value
covers both sides, but for an **unscoped owner with a scoped target** the owner's `owner_field` is
`None`. Falling back silently to an unscoped query puts other tenants' labels and ids in the dropdown —
the read-side leak FR-8 exists to close; falling back to empty options makes the form unfillable with
no signal. Both failures are invisible to the household pilot, which is uniformly scoped, so **S8
cannot catch this** — hence the generate-time guard and the dedicated S0 fixture.

**Where the loud failure surfaces — bounded by CRP R2 (R2-S3).** "Fail loud at generate time" is not
confined to `generate`: `_check_tenant_aware_drift` recovers the tenant from the file's own header
(L516) and calls `builders[kind]()` → `render_web(...)` with **no** exception handling (L520–527), and
`_re_render`'s `fastapi-web` lambda (L272) and `htmx-form` lambda (L279–281) are equally bare. A raise
from inside the renderer therefore escapes the drift API entirely, so `--check` and the
`owned_file_in_sync` skip-hook — the exact FR-ED-16 surface S7's last row exercises — would crash
instead of reporting, leaving a mixed-cell app unable even to run a drift check to find out why. The
existing raise-from-render precedent, `_validate_filter_fields` (L1281–1290, called at L1320), raises
for a bad **`views.yaml`** — an operator-fixable manifest error — whereas this cell is a *legal Prisma
schema shape*. Hence (d) prefers adding the principal, and bounds the blast radius of the alternative:
a typed error that the drift path converts to a diagnosable status.

Per (c), this is where `GET /ui/<e>/new` loses its anonymous 200 in scoped apps (see the S4
auth-posture note): generated content changes, drift dep-sets do not.

**Verify:** runtime, two principals each owning one Member — principal A's `/ui/chore/new` lists
only A's Member; `POST /ui/chore` as A with B's member id returns a 200 form with a field-level error,
writes nothing, and the error text is identical to the nonexistent-id case. Mixed cell, on the S0
unscoped-Chore × scoped-Member fixture — the emitted `_options_chore` query carries the owner predicate
and the route carries the `principal` dependency, **or** generation raises the named error; an
anonymous `GET /ui/chore/new` is refused rather than served unscoped, and an authenticated request
returns 200 with scoped options. Generator unit: no generated file contains an unfiltered
`select(<scoped target>)`; on that same fixture `check_drift` / `owned_file_in_sync` for `fastapi-web`
return a `DriftResult` (any status) rather than letting an exception escape, and if the raise branch is
taken the exception is the named generator error and the drift path converts it. Mixed fixture: a
picker-free entity's routes carry neither `session` nor `principal`.
