**From:** ContextCore loop orchestrator (Harbor SIL-REX) · **To:** startd8-sdk owners (observability scoring pipeline)

## TL;DR — one SDK fix, two symptoms

`observability-quality.json`'s **`aggregate`** block is missing the per-type scores for the **triplet artifact
types** — `dashboard_spec`, `alert_rule`, `slo_definition`. It emits `avg_runbook_score` (and
`loki_rule`/`notification_policy`) but **not** `avg_dashboard_spec_score` / `avg_alert_rule_score` /
`avg_slo_definition_score`. This single gap blocks two Harbor score levers:

- **L4** (structural B→B+): the report-card grader reads `avg_dashboard_spec_score` for the structural B+ rule
  (`composite>=0.65 AND dashboard>=0.90`). The key is absent → `dashboard=0.0` → structural caps at B despite
  every `dashboard_spec` scoring 0.9167.
- **L1a** (metric_cov ceiling): the same scored-set exclusion appears to zero **`metric_coverage_bridge`** for
  every service — the `alert_rule` content never enters the bridge bucket, so `avg_metric_coverage_score`
  can't exceed ~2/3 of its potential (blocks fidelity A).

If both trace to one root (the scored/aggregated set dropping the triplet types), **one SDK fix resolves both.**

## What the ContextCore grader consumes (grounded — so you know the exact contract)

The report-card grader is fully offline and reads **`{run_dir}/observability/observability-quality.json`** →
its top-level **`aggregate`** dict (via `contextcore.observability.catalog.load_quality_json` →
`report_card_policy.assemble_report_card`). It expects per-type keys named **`avg_{artifact_type}_score`**,
specifically `avg_dashboard_spec_score` (dashboards are `artifact_type == "dashboard_spec"`),
`avg_alert_rule_score`, `avg_slo_definition_score`, `avg_runbook_score`.

ContextCore side is already aligned: **PR #356** makes the structural grader read `avg_dashboard_spec_score`
(with a fallback to the plain `avg_dashboard_score`). It is **inert until the SDK emits the key** — verified
against the real Harbor audit: the fix reads the right key, but the key isn't there.

## The locus (where it's produced)

`_write_quality_report()` (`artifact_generator.py:2565`) writes `observability-quality.json`. Its `aggregate`
is built at **2694-2704**:

```python
scored = [a for a in artifacts if a.quality and "score" in a.quality and a.status == "generated"]  # :2593
...
by_type = {}
for a in scored:                                   # :2697
    by_type.setdefault(a.artifact_type, []).append(a.quality["score"])
for atype, scores in by_type.items():              # :2704
    aggregate[f"avg_{atype}_score"] = round(sum(scores)/len(scores), 4)
```

The **same `scored` set** also populates the per-service coverage buckets at **2624-2630**
(`svc_bridge_contents` ← `alert_rule`/`loki_rule`/`notification_policy`; `svc_system_contents` ←
`slo_definition`; `svc_human_contents` ← `dashboard_spec`).

## The contradiction we need YOU to resolve (why we're handing this off, not patching blind)

If `dashboard_spec` were in `scored`, then **both** `svc_human_contents` (human coverage) **and**
`avg_dashboard_spec_score` would be populated. Harbor's real data shows **human coverage moved** (exporter
0.864) but **`avg_dashboard_spec_score` is absent**, and **`metric_coverage_bridge = 0`** for all services
even though `alert_rule` artifacts are generated. Those can't all come from one consistent `scored` set — so
one of these is happening, and you own the code that knows which:

1. `observability-quality.json` is **stale** in the pilot's durable-audit path (not regenerated by the run
   that produced the SCORECARD `score_matrix` where human=0.864 / dashboard_spec=0.9167 live) — so its
   aggregate predates triplet scoring; **or**
2. the triplet artifacts are **dropped from `scored`** at `:2593` after the affordance bind / rescore lanes
   (`_apply_affordance_*` @ 1874-1887, `_rescore_dashboard_specs_after_binds` @ 1895) — e.g. their `status`
   is no longer `"generated"`, or `a.quality` loses the `"score"` key, while `runbook`/`loki_rule`/
   `notification_policy` (untouched by the binds) survive; **or**
3. the aggregate the grader reads and the per-service coverage are computed from **different lists/points**.
