## 0. Why this exists — the asymmetry this closes

The deterministic **$0 codegen path is Python-only by design**: `backend_codegen/` projects a `schema.prisma` contract → a FastAPI/Pydantic/SQLModel/HTMX app as a pure function, registered as a deterministic provider under `startd8.contractors.deterministic_providers`. For **Go/Java/C#/Node.js the second (LLM-driven) path does the RENDER work too** — the model produces the skeleton *and* the structure, not just the irreducible business logic. But `languages/` already has the mature per-language *read* half for Go: `go_parser.py` (regex structure extraction), `go_splicer.py` (brace-matching body splicing), `go.py` (`GoLanguageProfile`: `go.mod` gen, gofmt/goimports, stub detection, semantic checks). **What's missing is the WRITE half — a deterministic Go RENDERER** — so the LLM is paying to emit boilerplate a pure function could.

This pilot builds that renderer for **Go first** (most mature tooling; the Round-3 fleet's productcatalog/shipping/checkout backends are Go). It **tiers** the work: skeleton ($0 render) / simple elements ($0 template) / moderate (micro-prime) / complex (LLM splice), so the LLM is charged only for irreducibly-complex bodies. It emits **realization provenance** (regime=`deterministic` for rendered skeleton, `llm` for spliced bodies) so `navigator/realization.py`'s determinism-% scoreboard **measures the lift** the pilot delivers.

## Design decisions

- **Extend, don't duplicate, `proto_codegen/skeleton_go.py`.** The single biggest grounding fact: a deterministic Go gRPC server skeleton (package/imports, `type <svc>Impl struct{ pb.Unimplemented<Svc>Server }`, per-RPC stub methods, `main()` bootstrap with `PORT`/health-server) **already ships** as `render_go_skeleton`, registered as the `proto-skeleton` provider. **Lean on protoc for the wire layer** (proto → Go interfaces/DTOs/(de)serialization is protoc's job, already deterministic); this renderer renders the **service-internal skeleton *around*** that wire stub — additional domain structs, helper interfaces, wiring, the parts `skeleton_go.py` leaves as `Unimplemented`.
- **Mirror `backend_codegen`'s provider shape** (FR-6): a `go_codegen/provider.py` `GoSkeletonProvider` implementing `owns`/`is_in_sync` against the contract, registered under `startd8.contractors.deterministic_providers`, recognized by the prime-contractor skip-hook as `$0.00`-owned.
- **Reuse the Go read/splice side, don't rebuild:** `go_splicer.splice_body_into_skeleton` (bodies), `go.py` (`go.mod` gen, gofmt/goimports cleanup, `go_semantic_checks`), `go_parser.py` (element extraction), `micro_prime/engine.py`'s Go branch (moderate tier).
- **Determinism is the product.** The lift is only real if it's measured: every rendered element stamps `regime=deterministic`, every spliced body `regime=llm`, feeding `realization.corpus_realization` / `determinism_pct`.

## Overview

`startd8 generate go --contract <proto|prisma>` reads a contract IR and renders a Go **service-internal skeleton** (packages, domain structs, interfaces, DTOs and their (de)serialization, `go.mod`, `main`/bootstrap) as a pure $0 function, leaning on protoc for the gRPC wire layer and extending the already-shipped `render_go_skeleton`. Each element is **routed by complexity tier**: skeleton/boilerplate → $0 render; simple elements (e.g. a count loop) → $0 template; moderate → micro-prime; complex/business-logic → LLM body spliced via `go_splicer`. The output is verified by Go semantic checks + SARIF, stamps realization provenance so the determinism-% scoreboard measures the lift, and is proven on the Round-3 Go services (productcatalog/shipping/checkout). $0 for the skeleton, additive, byte-identical where deterministic.

## Objectives

- **O-1:** A contract projects into a compilable Go service-internal skeleton at $0 — target: `generate go --contract <c>` emits packages/structs/interfaces/DTOs/`go.mod`/`main` deriving from the contract, leaning on protoc for the wire layer, with no LLM call for the skeleton.
- **O-2:** Tiered + honest — target: each element is routed to $0-render / $0-template / micro-prime / LLM by complexity tier; only irreducibly-complex bodies reach the LLM (spliced via `go_splicer`); business logic is a non-goal.
- **O-3:** Measured lift + registered + piloted — target: the renderer registers as a deterministic provider, stamps realization provenance, verifies via Go semantic checks + SARIF, and its determinism-% lift is measured on the Round-3 Go services.

## Non-requirements

- **NR-1:** Does NOT render Java, C#, or Node.js — this is the **Go pilot only**; the other four languages are the reflective-adoption follow-up once the per-language render pattern is proven on Go (the most mature tooling).
- **NR-2:** Does NOT generate business logic — the quote formula, the pricing rule, the domain algorithm are **irreducibly LLM** (bucket 3/4); the skeleton leaves them `panic("not implemented")` stubs and routes them to the LLM tier (FR-2). The renderer's scope is the skeleton, not the value.
- **NR-3:** Does NOT hand-render the gRPC wire layer — proto → Go interfaces/DTOs/(de)serialization is protoc's job (FR-3); the renderer must never duplicate or drift from the protoc-generated `pb` package.
- **NR-4:** Build-ready — `go.py`/`go_parser.py`/`go_splicer.py` (Go read/splice), `proto_codegen/skeleton_go.py` (the gRPC skeleton to extend), `realization.py` (the scoreboard), `complexity/classifier.py` (tiering), and the Round-3 Go reference fixtures are all present.
- **NR-5:** Does NOT change the Python deterministic path — `backend_codegen`/`frontend_codegen`/`scaffold_codegen`/`view_codegen` are unchanged; `go_codegen` is a sibling under the same provider group, not a modification of the Python renderers.
